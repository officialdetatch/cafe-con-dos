# Café Con Dos — website

Static site (plain HTML/CSS/JS, no build step; articles come from a Sanity editor) for **Café Con Dos, an independent media platform**: articles, interviews, opinions and cultural discoveries, the Sobremesa section, and the podcast archive. Interface in Spanish (with the brand's natural Spanglish), tagline in English ("Stories worth discovering. Perspectives worth sharing."), articles in either language. Light/dark switch. Deployed to GitHub Pages by a GitHub Action (`.github/workflows/deploy.yml`); opens locally by double-clicking `index.html`.

The text and layout of every page are plain HTML in its `.html` file. JavaScript only fills in what changes (article and episode lists, filters, the featured article) and runs the buttons and forms. See **How to edit the site** below.

## How to edit the site

**Page text** (titles, paragraphs, buttons, the Nosotros story, the Contacto cards and form): open that page's `.html` file and edit it like any HTML. Comments in the files point out the parts the site fills in by itself.

**Header, footer and newsletter block**: they appear on every page, so each one lives in a single file in `partes/`:

1. Edit `partes/encabezado.html`, `partes/pie.html` or `partes/boletin.html`.
2. Run `node scripts/partes.js` from the repo folder. It copies the part into every page (between the `<!-- parte: … -->` and `<!-- /parte: … -->` marks), so you can check it locally.
3. Commit and push. If you forget step 2, the publish step does it anyway, so the live site is always right.

Don't edit the header or footer inside a page: the next copy overwrites it. The comment at the top of each copy says where its source is.

| To change… | Edit |
|---|---|
| Footer text, links or social icons | `partes/pie.html` |
| Menu links, the Suscríbete button | `partes/encabezado.html` |
| Newsletter title, text, button | `partes/boletin.html` |
| Home: tagline, sections, YouTube player, "Más que una conversación" | `index.html` |
| Home picture when no article is featured | `index.html`, inside `<figure class="hero-figura" data-destacado>` |
| The video in "Del archivo" | `index.html`, the `<iframe>` (comment explains how to show one fixed video) |
| Host bio and photo | `nosotros.html`, the `<div class="host">` block |
| Who writes (name, role, photo) | `assets/js/config.js` → `hosts` (see "Writers" below) |
| Contact cards, form questions, reasons list | `contacto.html` |
| Labels of filters, form messages, pop-up text | `assets/js/textos.js` |
| Sections, topics, series | `assets/js/config.js` (then `npm run deploy` in `studio/` so the editor picks them up) |
| Colors, spacing, fonts | `assets/css/styles.css` |

Social links are written where they appear (`partes/pie.html`, `contacto.html`, the buttons in `index.html`) and also in `redes` in `config.js`, which the episode pages use. If one changes, search the repo for the old link and replace it everywhere.

## Email alerts for new articles and episodes (Brevo + GitHub Actions)

When an article or an episode is published, the site emails the Brevo list once: brand-styled email with the cover, section, title, summary and a "Leer el artículo" button. It works like the "News alert email" on LPBLSA, and it is **off until you turn it on**.

- **How it runs:** `.github/workflows/aviso-articulos.yml` starts right after "Publicar sitio" finishes OK (every Sanity publish, every push, and the 6 am run that releases scheduled posts). It runs `scripts/aviso-correo.js`, which waits until the article is live on the site, then creates the campaign in Brevo and sends it.
- **No duplicates:** each article becomes a Brevo campaign named `Aviso: <article id>`; if one exists, it is skipped. Edits to an old article send nothing.
- **Only what is new:** it only emails articles published on or after `AVISOS_DESDE`. With that variable empty, nothing is sent, so articles can be uploaded before launch without emailing anyone.
- **Safety stop:** if more than 3 articles would go out at once, it sends nothing and the run fails. Send them one by one with "Run workflow".
- **Scope:** articles, Sobremesa posts **and episodes**. Episodes come from `data/episodios.js` (added with the episode writer): when you push a new one, the site publishes and the alert goes out right after. The email says "Nuevo episodio · <series> · Ep. N", uses the YouTube thumbnail (or `portada` if the episode has one), shortens the YouTube-style title (drops the " | series | Ep. #N" tail) and has an "Escuchar el episodio" button. Episode campaigns are named `Aviso episodio: <episode id>`.
- **Old episodes are safe:** archive episodes added with an old `fecha` (a day other than today) are never emailed, even if you upload them after launch. Only an episode whose `fecha` is today (or later, once that day arrives) goes out. To email an old one on purpose, use "Run workflow" with its id.

**One-time setup**
1. **Brevo API key**: *SMTP & API › API Keys › Generate a new API key*. Copy it right away (it is shown once).
2. **List ID**: *Contacts › Lists*; the number next to your subscriber list.
3. In the GitHub repo: **Settings › Secrets and variables › Actions**
   - tab **Secrets** › New repository secret: `BREVO_API_KEY` = the key.
   - tab **Variables** › New repository variable, one each:
     `BREVO_LIST_ID` (the number), `SENDER_EMAIL` (`newsletter@cafecondos.com`), `SENDER_NAME` (`Café Con Dos`), `REPLY_TO` (`info@cafecondos.com`).
   - Leave `AVISOS_DESDE` **out** for now.
4. Make sure the sender is verified in Brevo (*Senders, domains, IPs*), and that the **Brevo RSS integration is not active** (both on = two emails per article).

**Test it** (GitHub › Actions › *Aviso por correo* › Run workflow). `story_id` is what comes after `?id=` in the article's URL.
- `dry-run`: no email; the run saves a preview (download the `email-preview` artifact at the bottom of the run).
- `test`: emails only the address you type, as a Brevo test.
- `send`: emails the whole list. Check "force" to resend one that already went out.

**To turn it on at launch:** add the variable `AVISOS_DESDE` with the launch moment in UTC, for example `2026-11-01T00:00:00Z`. Articles published from then on are emailed automatically. To turn it off, delete the variable.

## Shop (Fourthwall)

The store itself lives on Fourthwall: **https://cafe-con-dos-shop.fourthwall.com** (products, cart, payments, shipping, all managed there). `tienda.html` on cafecondos.com shows the products **live**: every time someone opens the page, it asks Fourthwall's Storefront API for the current list. A new product, a price change, a sale price or a sold-out item shows up by itself, with no push and no rebuild.

- **Settings:** `tienda` in `assets/js/config.js`: `url` (the shop address), `token` (Fourthwall → Settings → For developers → Storefront API; it's a public, read-only token: it can list products but can't see orders, money or customers), `coleccion` (`all`, or a collection's slug to show only that collection), `moneda`.
- **What each card shows:** the first photo (the second one appears on hover), the name, the price ("Desde $X" when variants cost different amounts), the crossed-out old price and an "Oferta" tag when there's a compare-at price, and "Agotado" (moved to the end) when sold out. Hidden or members-only products are skipped. Each card opens the product on Fourthwall in a new tab, where people add it to the cart and pay.
- **Texts** ("Sirviendo la tienda…", "Agotado", etc.) are the `tienda.*` keys in `assets/js/textos.js`; the page title and intro are in `tienda.html`.
- **"Antes de comprar" box** (below the products, written in `tienda.html`): all sales final (made to order; no returns, exchanges or refunds, including size, except misprints/visible defects reported within 30 days with photos), cancel or edit only before production via the confirmation email link, Fourthwall handles production, shipping, payments and order support (Café Con Dos isn't responsible for shipping delays or losses), international orders may owe customs fees, plus links to the shop's Returns & FAQ, Terms of Service and Contact pages. It summarizes Fourthwall's Returns & FAQ page as of Oct 2026; if Fourthwall changes its policies, update the box.
- **If Fourthwall is down** the page says "No pudimos cargar los productos ahora mismo" and keeps the "Ver la tienda completa" button.
- **Shop look:** `fourthwall-estilo-cafecondos.html` (kept outside the site files) is the block of code that dresses the Fourthwall shop in the same colors, fonts (Antonio + Literata), rounded "bubble" corners and paper texture as the site, with dark mode following the visitor's device. It goes in Fourthwall → Site design → Style → Edit HTML code → Header code. The logo, the hero text ("Bold new looks") and the menu links are set in Fourthwall's own editor (Site design), not in code.

## Weekly newsletter ("Boletín"): written in the Studio, sent by email only

A tab called **Boletín** in the Studio (next to Artículos and Comentarios). It never appears on the website: it only goes out by email to the Brevo list. The layout is fixed (logo, big title, the date range, a greeting, one block per entry with an optional photo, a closing, and a footer with "Síguenos en nuestras redes…" and the social links), so nobody has to design a template in Brevo.

**Writing one (what she does):**
1. Boletín tab → **Crear** (new). The title is already "Lo que viene esta semana".
2. **Enviar el**: the day it goes out (6:00 am, RD). Required.
3. Optional **Saludo**; then **Lo que viene**: add one entry per thing (date, optional label like "Nuevo episodio", title, a few lines of text, optional photo, optional link). Entries are sorted by date automatically.
4. Optional **Despedida**.
5. Check the **Vista previa del correo** tab (shows the real email, light or dark mode, updating as she types).
6. **Publicar**. It asks for confirmation and says when it will go out. A draft never goes out; only a published boletín does.

**How it goes out:** `scripts/boletin-correo.js`, run by `.github/workflows/boletin.yml` right after every "Publicar sitio" (each Sanity change and every morning at 6:00 am). It sends published boletines whose "Enviar el" day has arrived. Safety rules:
- **Off until launch**: it uses the same `AVISOS_DESDE` repository variable as the article alerts. Empty = nothing goes out automatically. (Manual runs below always work.)
- **Once only**: before sending it looks in Brevo for a campaign whose name ends in the boletín's id (`Boletín: … [id]`). Editing and re-publishing a boletín that already went out does **not** resend it.
- A boletín whose date passed more than 3 days ago is not sent automatically, and if two are due at once nothing is sent (the run fails on purpose; send them one by one).
- The email uses the same Brevo variables as the article alerts (`BREVO_API_KEY` secret; `BREVO_LIST_ID`, `SENDER_EMAIL`, `SENDER_NAME`, `REPLY_TO`).

**Trying it (do this once before launch):** GitHub → Actions → **Boletín por correo** → Run workflow. Type `ultimo` (or the boletín's "Enviar el" date, `AAAA-MM-DD`), mode **test** and your own email: Brevo sends you a copy only to you. `dry-run` just saves the HTML (download it from the run's "boletin-preview" artifact); `send` mails the whole list (add `force` to resend one that already went out). The boletín must be **published** in the Studio.

**One-time setup:**
- In sanity.io/manage → your project → API → **Webhooks**: the existing webhook that triggers "Publicar sitio" must also fire for boletines. If it has a filter like `_type == "articulo"`, change it to `_type in ["articulo", "boletin"]` (an empty filter already covers everything). Without this, a boletín dated today would wait until the next morning's run.
- Studio: Netlify redeploys moderador.cafecondos.com on push (and run `npm run deploy` in `studio/` if you also use the cafecondos.sanity.studio copy).
- Footer wording ("Síguenos en nuestras redes…") and the layout live in `scripts/boletin-html.mjs`. The Studio's preview uses a copy of that file made by `studio/sincronizar.mjs` (`studio/generado/`), so there is only one template.
- The Sanity dataset is public-read by default, so a published boletín's text is technically readable through the API; keep truly confidential things out of it.

## Writers (who signs each article)

Several people write for the site (Allie → Editora en jefe, Sarah → Columnista, others later). They live in `assets/js/config.js` → `hosts`: `id` (no accents/spaces, never change it after articles use it), `nombre`, `rol` (shown under the name) and `foto`.

- **In the Studio:** each article has **Escrito por**, a required choice (shown only when there are 2+ people). Nothing is pre-selected, so nobody gets credited by accident.
- **On the site:** the article shows the photo, "Por <name>" and the role. Sobremesa cards show "Por <name>". Articles with no author fall back to the first person in `hosts` (keep Allie first).
- **Photos:** put them in `images/autores/` (square, under ~200 KB) and write the path in `foto`, e.g. `"images/autores/sarah.jpg"`. Empty = the cup. (`studio/static/` is only for the Studio's own icons, not for writers.)
- **Add a writer:** copy a `{ … }` block in `hosts`, push, and run `npm run deploy` in `studio/` (or let Netlify rebuild moderador.cafecondos.com, which happens on push). The new name then appears in "Escrito por". Their bio on "Nosotros" is a copy of the `<div class="host">` block in `nosotros.html`.

## Admin panel: moderador.cafecondos.com (Studio + comment moderation)

A private copy of the editor, hosted on Netlify at `https://moderador.cafecondos.com`, so posts can be written and comments moderated from a phone. It has two tabs: **Artículos** (the normal Studio) and **Comentarios** (every comment from the whole site, live, with a Delete button).

- **Hosting:** Netlify builds the `studio/` folder of this repo on every push (settings in `studio/netlify.toml`: base `studio`, command `npm run build`, publish `dist`, Node 22). DNS: a CNAME `moderador` → the `….netlify.app` address Netlify gives. The public site stays on GitHub Pages.
- **Who gets in (enforced by the services, not by hiding the page):**
  - *Articles:* only people invited as members in sanity.io/manage (Members). Sanity must also allow `https://moderador.cafecondos.com` under API → CORS origins, with "Allow credentials".
  - *Comments:* sign in with Google **or** with email + password (Firebase Authentication). A person can delete only if (1) their email is **verified** and (2) a document named exactly like their email (lowercase) exists in the Firestore collection `ccd_admins`. Emails are never stored in the repo. The rules are in `firestore.rules`. Google accounts are verified automatically. Email + password accounts start unverified; the tab has a "Enviar correo de verificación" button. The verification rule is deliberate: without it, a stranger could register someone else's email with their own password.
- **Add or remove a moderator:** Firebase console → Firestore Database → `ccd_admins` → add a document whose ID is the email (any field, e.g. `rol` = `moderador`). Delete the document to remove them.
- **Adding a person who uses email + password:** (1) Firebase → Authentication → Sign-in method → **Email/Password** → Enable (leave "Email link" off). (2) Authentication → Users → **Add user** with their email and any temporary password. (3) Add their email to `ccd_admins` (above). (4) They open the Comentarios tab, tap **Crear o cambiar mi contraseña**, set their own from the email Firebase sends, then sign in; if the tab asks to verify, tap **Enviar correo de verificación**, open the link, then **Ya lo verifiqué**. Optional: Authentication → Settings → User actions → turn off "Enable create (sign-up)" so strangers can't create accounts at all.
- **Firebase setup (once):** Authentication → Sign-in method → Google → Enable. Authentication → Settings → Authorized domains → add `moderador.cafecondos.com` (and the `….netlify.app` address while testing). Firestore → Rules → paste `firestore.rules` → Publish.
- **Code:** `studio/herramientas/Comentarios.jsx` (the tab) and `studio/herramientas/nube.js` (Firebase, loaded from Google's CDN like the public site; no extra npm packages). The tab reads the Firebase keys from `comentarios.firebase` in `config.js` through `studio/sincronizar.mjs`.
- **Icon / logo:** the envelope-with-cup logo (made by the host) is the browser-tab icon, the iPhone Home Screen icon and the Studio's top-bar icon. Files in `studio/static/`: `favicon.svg`, `favicon.ico`, `favicon-96.png`, `favicon-192.png`, `favicon-512.png`, `apple-touch-icon.png` (the names Sanity looks for) and `logo-moderador.png` (top bar). To change it, replace those files (same names) and hard-refresh; browsers cache icons. On iPhone: Safari → Share → Add to Home Screen.
- **Brand colors:** the whole editor uses the site's palette (café `#723F40`, espuma `#FBF3EC`, dark `#221415`) through `buildTheme` from `@sanity/themer` in `studio/sanity.config.js` (light and dark). The Comentarios tab has its own matching palette in `Comentarios.jsx` (`COLORES`) and loads Antonio + Literata from Google Fonts. The theme code tries both option shapes `@sanity/themer` has used (per-scheme `light`/`dark` groups, or one set) and, if neither works, falls back to Sanity's default colors instead of breaking the editor (a warning appears in the browser console). To remove the theme on purpose, delete the `construirTema` function and the `...(tema ? {theme: tema} : {})` line from `sanity.config.js`. `@sanity/themer` is listed as `latest` in `studio/package.json`; run `npm install @sanity/themer` inside `studio/` once to pin it to an exact version and commit `package.json` + `package-lock.json`.
- `https://cafecondos.sanity.studio` keeps working in parallel; it can be dropped once the panel is proven.

## Sections

En Portada (enportada.html, formerly Explorar) has four sections, set in `secciones` in `config.js`: **Historias y entrevistas**, **Cultura y descubrimientos**, **Opiniones y perspectivas** and **Sobremesa**. Each has a name, a short label (used on the color block of an article without a photo) and a description (shown in En Portada when the section is picked). Sobremesa also has its own page. The cards in "Empieza a explorar" on Inicio are written in the home page (`cafenotready.html` until launch, then `index.html`); each one shows the photo of the newest article in its section, and the fourth one, "Conversaciones", the newest episode.

Every article has one section, a language (`es` or `en`), topics, and optionally a cover photo with its description, people featured, a related episode and the "Destacar en la portada" checkbox. The newest highlighted article is the big one at the top of Inicio; with none highlighted, the newest article is used. Articles without a photo get a block in the section's colors.

## Day-to-day

**Articles (her):** she opens the editor (`https://<name>.sanity.studio`), signs in with Google, writes, and hits **Publicar**. About two minutes later the article is on the site, in En Portada/Sobremesa, in `feed.xml` (so the Brevo email picks it up) and in `sitemap.xml`. Editing a published article, **Despublicar** or **Borrar** works the same way: the site updates itself. Nobody commits anything for her articles; they never touch the repo.

**Episodes (you):**

1. Open `writers/episodio-writer.html` in the browser.
2. Fill the form. Live preview on the right.
3. **Agregar a la lista** → **Descargar episodios.js** → replace `data/episodios.js`.
4. Commit and push. The Action publishes the site and rebuilds `feed.xml` and `sitemap.xml` on its own. The editor's "Episodio relacionado" list reads the published episodes, so new ones show up there after the push.

A future date schedules an item (in the editor or the writers): it appears on the site at 6:00 am Dominican time on that date, at the same moment for every visitor worldwide, and the daily 6:00 am run adds it to the feed with no extra push. The editor lists those under **Programados**.

`writers/articulo-writer.html` still works as a backup for articles kept in the repo. The sample content is marked `"ejemplo": true` and shows an "Ejemplo" badge. The **Borrar los ejemplos** button in each writer removes it in one go. Sample items are never included in the feed or sitemap.

## Article editor (Sanity) — one-time setup

What she gets: a private page with her login, a form in Spanish with the same fields as the site (title, section, language, date, cover photo with focus point, summary, the article with section titles/subtitles/lists/quotes/links and as many photos as she wants between paragraphs (in the body, tap + → Foto; each photo has an optional caption and a description), topics, "Destacar en la portada", people in the story, related episode), and buttons to publish, unpublish, delete and **Ver en la página**. Sections, topics and the host come from `config.js`, so there is one place to change them.

How it connects: when she publishes, Sanity sends a webhook to GitHub, which runs `deploy.yml`. The Action pulls every **published** article from Sanity (`scripts/contenido-sanity.js`), adds them to the ones in `data/articulos.js`, then builds the feed and sitemap and publishes. Drafts are never read. If Sanity can't be reached, the run fails on purpose and the live site stays as it was. The daily 6:00 am run also pulls from Sanity, so even if the webhook ever fails, her posts are up by the next morning.

Sanity's free plan covers this: 20 users, 2 webhooks (this uses 1), 100 GB of photos. On the free plan the dataset is public, which only means published articles can be read through Sanity's API (they're on the site anyway); drafts stay private.

You need Node 22.12 or newer on your computer for steps 3–4.

1. **Create the project.** Sign up at [sanity.io](https://www.sanity.io) (Google login is fine). In [sanity.io/manage](https://www.sanity.io/manage), create a project called *Café Con Dos*. Under **Datasets**, make sure there's one named `production` (create it if not). Copy the **Project ID** into `sanity.projectId` in `assets/js/config.js`.
2. **Try it on your computer.** In a terminal: `cd studio`, `npm install`, `npm run dev`, then open http://localhost:3333 and sign in. If it asks to allow http://localhost:3333 as a CORS origin, follow its link and allow it (with credentials). Write a test article and publish it (the site only picks it up after step 6).
3. **Put it online.** `npm run deploy`. The first time, it asks for a name: type `cafecondos` (the address becomes https://cafecondos.sanity.studio). It then prints an `appId`; paste it into `sanity.studioAppId` in `config.js` (only needed for the optional step 7). Run `npm run deploy` again whenever you change `studio/` or the sections/topics/host in `config.js`.
4. **Invite her.** In sanity.io/manage → **Members** → **Invite**: her email, role **Administrator** (the free plan only has Administrator and Viewer, and Viewer can't publish). She accepts the email and signs in with Google.
5. **GitHub token.** GitHub → Settings → Developer settings → **Fine-grained tokens** → Generate. Repository access: **only this repo**. Permissions → Repository → **Contents: Read and write**. Pick the longest expiration offered and put a reminder on your calendar to renew it (when it expires, her posts still go up, but only at the 6:00 am run, until you paste a new one in step 6).
6. **Webhook.** sanity.io/manage → your project → **API** → **Webhooks** → Create:
   - Name: `Publicar sitio`
   - URL: `https://api.github.com/repos/OWNER/REPO/dispatches` (your user and repo name)
   - Dataset: `production`
   - Trigger on: **Create**, **Update** and **Delete** (Unpublish counts as Delete)
   - Filter: `_type == "articulo"`
   - Projection: `{"event_type": "sanity", "client_payload": {"titulo": titulo}}`
   - HTTP method: `POST`
   - HTTP headers: `Authorization` = `Bearer <the token from step 5>`, and `Accept` = `application/vnd.github+json`
   - Leave drafts/versions off and the API version as is.
7. *(Optional)* **Editor republishes itself.** With the `appId` in `config.js`, create a token in sanity.io/manage → **API** → **Tokens** with the **Deploy Studio** permission and save it in GitHub → Settings → Secrets and variables → Actions as `SANITY_AUTH_TOKEN`. From then on, `studio.yml` republishes the editor whenever `studio/` or `config.js` changes (e.g. you add a topic). Without it, that workflow just leaves a note and skips.
8. **Clean up the samples.** Once her real articles are in, empty `data/articulos.js` with **Borrar los ejemplos** in the article writer. If the same address exists in both places, the editor's version wins; but if she later deletes it in the editor, the repo copy would show again. An empty `data/articulos.js` avoids that.

**Test it live (5 minutes):**

1. In the editor, publish an article called "Prueba". In GitHub → **Actions** a run named **Editor: Prueba** appears. When it turns green (1–2 minutes), click **Ver en la página** in the editor.
2. Change a word and publish again → new run → the change is on the page.
3. **Borrar** (or **Despublicar**) → new run → the page says the post wasn't found, and it's gone from En Portada, `feed.xml` and `sitemap.xml`.
4. If no run appears: sanity.io/manage → API → Webhooks → your webhook → **Attempts log**. 204 means GitHub accepted it; 401/403 is the token (step 5); 404 is the URL or token repo access; 422 is the projection.

Notes:

- **Comments stay as they are.** They're stored in Firebase under the article's address. The editor creates the address from the title on the first publish and locks it after that, so links people shared, the Brevo emails and the comments keep working even if she changes the title. Deleting an article doesn't delete its comments (they'd come back if an article with that address were published again); delete them in the Firebase console if needed.
- **Photos** live in Sanity and are served resized from its CDN. The focus point she marks is used so cards don't crop faces.
- **Local preview:** opening `index.html` from the folder only shows articles in `data/articulos.js`. The live site has hers too.
- To read from a private dataset (paid plans), add a `SANITY_READ_TOKEN` secret in GitHub; the Action already passes it along.

## Light and dark theme

The background has a paper texture (fine grain plus soft mottling) drawn with inline SVG, so there are no image files. It is set by `--textura-grano` and `--textura-nube` at the top of `assets/css/styles.css`; set both to `none` to remove it, or lower the last two numbers of each `feColorMatrix` to soften it. The header gets a soft shadow (`--sombra-nav`) once you scroll.

The site follows the visitor's system setting. The moon/sun button in the header switches it, and the choice is remembered in that browser (`localStorage` key `ccd-tema`, applied as `<html data-theme="light|dark">` before the page paints, so there's no flash). Colors are tokens at the top of `styles.css`. The writers follow the same choice.

In dark mode the "Café para llevar" block and its pop-up become a toasted panel with an orange button instead of a full orange block (tokens `--boletin-*`), and the cup swaps to its light version.

## Design system (how the site looks)

The idea: *café con dos* is a conversation between two, so the design leans on two devices from the logo and nothing else.

- **Two voices.** Two-sentence titles read as a reply: the second sentence sits a little further in, in the accent color (the home tagline, "Ya casi sube el café. ¿Te servimos una taza?" and the footer tagline, whose two sentences are wrapped in `<span>`s in `partes/pie.html` for that). Section and page headers do the same: headline on the left, the sentence that answers it on the right (on wide screens).
- **The speech bubble** (the saucer in the logo) is used only where something "speaks": the featured story on the home page, the video frame, quotes inside articles, comments, the reader phrases on Nosotros, the support box, the newsletter and its pop-up. The little orange bubble before section labels is the same shape, small.
- **Type:** Antonio for headlines, labels and buttons (labels are shown as written, not forced to uppercase); Literata for reading, with its italic only for quotes, standfirsts and captions. Articles use a centered reading column (`--medida`), photos inside the text are a bit wider than the column, and the first letter is a drop cap in browsers that support it.
- **Motion** (end of `styles.css`, "Movimiento"): the home tagline arrives in two voices and steam rises off the featured story; the pre-launch title does the same. Everything else only answers the visitor: the menu icon turns into an X, links and filters underline, pages cross-fade when you change page, the reading bar fills as you scroll an article, and the theme switch opens the new palette in a circle from the button (`app.js`, theme button). With "reduce motion" turned on, all of it is off.
- The menu icon in `partes/encabezado.html` is three separate lines (`raya-1`…`raya-3`) so it can turn into an X; keep them if you edit the header.

## Language

Page text lives in each `.html` file and in `partes/`; the texts JavaScript needs (filters, form messages, pop-ups) are in `assets/js/textos.js`. Everything is in Spanish with the everyday Spanglish the brand uses (host, email, link, show notes, timestamps, collab…). The tagline stays in English on purpose. `lang="es"` is set on every page, the tagline and English articles carry `lang="en"`, so screen readers pronounce them correctly and Chrome/Safari offer translation sensibly. Brand names (Café Con Dos, Sobremesa, Entre Elementos) are marked `translate="no"`.

## Pop-ups

A visitor sees at most one interruption per visit: on the home page, the newsletter pop-up (after `popupSegundos` or 55% scroll, then not again for 14 days or after subscribing); on other pages, the "Invítanos un café" alert next to the cup button (after `avisoSegundos`, once a week). On phones the cup button steps aside while someone is typing in a form.

## SEO notes

- Each page has its own title and description; the home page carries Organization + WebSite (with site search) structured data, the archive carries PodcastSeries, and each article adds BlogPosting data when it loads.
- `sitemap.xml` lists every page, article and episode (except samples and scheduled items).
- Articles and episodes render with JavaScript from `?id=`. Google indexes these fine, but link previews on WhatsApp/Instagram use the site-wide share image (`images/og-cafe-con-dos.jpg`, with the tagline) and description. If per-article previews become important, the next step is having the Action also generate a small static HTML page per article (it already has all the data at that point).

## Notes

- **YouTube "Error 153" on your computer:** YouTube's players refuse to play on a page opened straight from a file (double-clicking `index.html`), because there is no website address to send them. On cafecondos.com they play. To preview locally with working videos, run `npx serve` in the repo folder and open the address it prints (or use VS Code's Live Server).
- **Images:** keep them small. The cup (`images/taza.png`, `taza-clara.png`) is shown at most ~300 px wide, so 600 px is plenty; the favicon is 48×48 and the iPhone icon 180×180. A photo for articles or the host works well at ~1600 px wide as a JPG.
- `feed.xml`, `sitemap.xml` and `data/episodios.json` (the editor's episode list) are not in the repo; the Action builds them into the published site. To rebuild by hand, use **Actions › Publicar sitio › Run workflow**, or run `node scripts/build-feed.js out/` locally.
- The writers stamp each new item with `publicado` (the moment it was added); the editor's **Publicar** button does the same on an article's first publish. The feed dates an item at 6:00 am Dominican time on its `fecha`, or at that `publicado` time if it was added later that same day, so an item pushed after the daily email still counts as new for the next one. Old items added later keep their original date, so they are not emailed as new.
- Upgrading from the previous version: `data/sobremesa.js` and `writers/sobremesa-writer.html` are replaced by `data/articulos.js` and `writers/articulo-writer.html`. If an old `data/sobremesa.js` is still around, the site and the feed read its posts as Sobremesa, but it's best to delete it.
- GitHub pauses scheduled runs in public repos after 60 days without repository activity. Pushes and the editor's webhook still publish; re-enable the schedule from the Actions tab if it stops.
- Fonts: Antonio (display, matches the condensed logo lettering) + Literata (reading), loaded from Google Fonts as variable fonts (Antonio 400–700; Literata 400–700 and italic 400–600, with optical sizes).
- Colors come straight from the logo: latte `#E9CAB0`, café `#723F40`, naranja `#F47D50`.
